A short guide to where things live in this project, so you can find your way back later.

What the app does

A student team pastes a group assignment. The AI turns its grading criteria into weighted tasks, the team picks who does what with a fair share per person, and one click creates the tasks as assigned GitHub issues. After that, a dashboard reads GitHub by itself: close an issue and its card turns green. Nobody updates a status by hand.

The main pieces: app.py (the Flask routes and pages), referee/ai.py (asks Claude for the tasks), referee/github_client.py (talks to GitHub), referee/logic.py (fair share, what counts as done, the issue text), referee/store.py (projects and profiles as JSON files in data/), and templates/ + static/ for what you see.

One action, end to end: closing an issue turns its card green

The route through the code

A reference route: it was offered as a short tour; the learner had already tried the app end to end and chose a short recap instead.

  1. The dashboard asks for the status. static/js/dashboard.js, search for function refresh(. It calls the status URL when the page opens, every POLL_SECONDS (10) and when you come back to the tab. It never changes a status itself.
  2. The server asks GitHub. app.py, search for def status_payload. One call to GitHub through list_referee_issues() in referee/github_client.py, combined with the tasks the app saved.
  3. The rule for "done". referee/logic.py, search for def task_status. Closed as completed counts as done; closed as "not planned" or "duplicate" drops out of the totals (DROPPED_REASONS). Back in the browser, renderBoard() in dashboard.js draws the card green.

To change this, start here

  • How the AI makes tasks (how many, how they're worded): referee/ai.py, PLAN_INSTRUCTIONS.
  • The fair share: referee/logic.py, fair_share() and share_rows(); the live version while choosing is updateFairShare() in static/js/review.js.
  • What counts as done: referee/logic.py, task_status() and DROPPED_REASONS.
  • The text of each GitHub issue (including the team board link): referee/logic.py, issue_body().
  • The view-only board link: app.py, board_link(); set PUBLIC_URL in .env once the app runs online.
  • How often the dashboard checks GitHub: POLL_SECONDS in .env, read by poll_seconds() in app.py.
  • Colors, fonts and spacing: the tokens at the top of static/css/style.css (:root).
  • A sentence on a page: the page's file in templates/, for example the dashboard note in templates/dashboard.html ("A card turns green…"). Restart the app after changing a template.
  • The example assignment: samples/assignment-room-booking.md.

A practice to reuse

Keep one source of truth, and let everything else read it. The planning (devpost/prd.md, "Dashboard: Automatic Status") decided that only GitHub says whether a task is done. The code follows that: status_payload() reads GitHub on every refresh and nothing stores a status, so the board can't drift out of date. Tests in tests/test_logic.py pin the rule down, for example test_task_status_mapping and test_reopened_issue_is_open_again.

On another project: decide early where each piece of data truly lives, write it down in the plan, and make every screen read from there instead of keeping its own copy.

Run it again

In the project folder (PowerShell), with your keys in .env:

uv run flask --app app run  then open http://127.0.0.1:5000

Tests: uv run pytest. More in README.md.
